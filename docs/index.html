LUCKY_PASS

Every other eval scores this as a pass. It is the case this tool exists to find: the answer is correct, but the chunk it should have come from was never retrieved, so retrieval contributed nothing.

What to do: check the ablation column. If the answer is still right with retrieval disabled entirely, your test set is answerable from pretraining and isn't measuring your pipeline. Regenerate it from a corpus the model can't already know.

TRUE_PASS

The pipeline worked end to end. The right chunk was retrieved and the answer is grounded in it.

What to do: nothing. This is the number to protect. Re-run after any change to chunking, embeddings, or top-k and make sure it doesn't move.

GENERATION_FAILURE

Retrieval did its job. The correct passage was in the context and the model still produced a wrong answer.

What to do: the retriever is not the problem. Look at the prompt, where in the context window the chunk landed, and whether the chunk is too long for the model to use.

RETRIEVAL_FAILURE

The wrong context came back and the answer was wrong. This is the honest failure, and the easy one to catch.

What to do: open the report's retrieval rank column. If the right chunk is ranked 2 or 3, raise top-k. If it's absent entirely, the problem is chunking or embeddings.

The problem

A correct answer is not evidence that retrieval worked.

A RAG system can answer a question correctly while retrieving nothing useful for it. The model already knew the answer from its training data and never needed the context. Existing evaluation tools check only whether the final answer is correct, so they score this as a pass, and the retriever can quietly stop contributing without anyone noticing.

That failure is invisible until the questions move to something the model doesn't already know, which is usually the moment the system reaches real users.

How it works

Ground truth for retrieval comes from the corpus itself, so correctness and retrieval can be judged independently and then crossed.

01 · ingest Chunk the corpus

Each chunk gets a stable ID derived from its content. Same corpus in, same IDs out.

02 · generate Write the test set

An LLM writes questions per chunk, answerable only from that chunk. The chunk ID is recorded as the expected retrieval.

03 · run Run your pipeline

Your adapter returns the answer plus the chunk IDs it retrieved. Correctness and retrieval are scored separately.

04 · ablate Confirm the lucky ones

Every LUCKY_PASS candidate is re-asked with retrieval off. Still correct means retrieval was never needed.

Install and run

Python 3.11 or newer. Any OpenAI-compatible API works for the judge and generator.

pip install git+https://github.com/Aliismail293/rag-tester.git

Against your own corpus and adapter:

ragaudit ingest ./docs
ragaudit generate --n 100
ragaudit run --adapter my_adapter.py
ragaudit report --out report.html

Or run the whole bundled demo, three reports included:

docker compose up --build

An adapter is one function, query(question) -> RAGResponse, returning the answer, the retrieved chunk IDs, and the contexts it used.

Your pipeline needs to be indexed against the chunks ragaudit ingest produced so the IDs line up. If it isn't, every hit reads as a miss and the tool looks broken. The README covers this in detail.

v2: honest scores while you tune

Generate a question set that can't be gamed, then let ragaudit tune your pipeline against it, with the final score measured once on questions the search never saw.

01 · generate Questions that resist keyword search

Facts are extracted per chunk, questions are reworded away from the passage, and a second model verifies each one. Each question is assigned to dev or test once, by hash.

02 · evaluate Only re-run what changed

Results are cached by question, config and corpus version. Edited chunks retire their questions; a corpus change re-runs new questions plus a sample of old ones.

03 · tune Search on dev only

Grid, random, or an LLM reading dev failures proposes configs. The tuning code can't read the test split; a runtime lock and a static check enforce it.

04 · report Score once on the locked test set

Baseline and best are scored once each on test. A large dev-over-test gap is flagged as overfitting.

The toy pipeline tuned on the demo corpus: dev score per trial, baseline vs best on the locked test split, failure classes before and after. Built with the offline mock LLM.

Run the v2 demo offline, no API key needed:

sh demo/v2/run_demo.sh

Against your own corpus and pipeline:

ragaudit generate --corpus corpus.jsonl --verifier-model gpt-4o
ragaudit evaluate --adapter my_pipeline.py
ragaudit tune --adapter my_pipeline.py --search-space space.yaml
ragaudit report --kind tune --out tune-report.html
